# 读见项目决策记录

> 状态：CURRENT / 决策记录 SSOT  
> 更新日期：2026-08-27  
> 本文件记录已经确认的边界和取舍。新决策应追加，不得静默覆盖历史结论；被替代的结论必须说明替代关系。

## D-001：采用本地优先 + BYOD

- **状态**：已确认
- **决定**：书籍、阅读进度、提取缓存和知识晶体默认留在本机；用户自行配置 API Key、模型和 Endpoint。
- **原因**：保护隐私、避开版权内容存储、降低服务器和运维成本，也符合个人开发者的精力约束。
- **代价**：缺少云同步、跨设备和统一账号体验；自定义端点需要用户自行处理 CORS。

## D-002：当前不做云端订阅产品

- **状态**：已确认，长期有效，除非出现明确外部需求
- **决定**：不为了商业化强行引入账户、云端书库、服务器代理或订阅体系。
- **原因**：云端会带来客服、合规、数据安全、API 成本和持续运营负担，可能吞噬 Owner 的真实使用与内容生产时间。
- **说明**：BYOD 配置有成本，但这不是产品价值。未来可做低成本配置体验优化，不以此为由建设云端基础设施。

## D-003：产品中心从“阅读器”转为“知识提取器”

- **状态**：部分 SUPERSEDED（由 D-008、D-009 细化）
- **保留部分**：分页阅读是基础设施，结构化提取和主动理解比持续堆叠阅读器功能更优先。
- **被替代部分**：知识提取器不再是产品终点；近期定位升级为“阅读到观点”工作台，长期北极星为本地认知工作台。

## D-004：正式沙盘先文档、后代码

- **状态**：SUPERSEDED（由 D-010 替代）
- **历史决定**：现有 quiz 只视为轻量盲盒测验；曾计划在框架说明书和状态规格明确后考虑正式沙盘。
- **替代原因**：大型沙盘的成本与验证价值不匹配当前阶段，近期只验证轻量观点压力测试方法。

## D-005：CFI 精确溯源问题暂时封存

- **状态**：已封存
- **决定**：保留实验性章节/段落跳转，不继续在提取管线上投入精确 CFI 修复。
- **原因**：问题涉及 epub.js 0.3 对单章大书和嵌套文档的定位行为，投入产出比暂不明确。
- **替代**：可核对性优先通过章节、分块、原文片段、来源编号和轻量定位提供；CFI 不阻塞主线。

## D-006：内容账号与工具弱耦合

- **状态**：已确认
- **决定**：读见可以服务文章和视频素材，但不绑定某个账号或平台，不在代码中接入平台运营，也不要求任何账号互相导流。
- **原因**：内容生产是产品价值验证场；账号与平台变化不应改变软件架构边界。

## D-007：质量验证优先于继续堆功能

- **状态**：已确认
- **决定**：先用不同题材书籍建立质量基线，并记录真实内容生产结果。
- **原因**：单次提取跑通不能证明泛化；真正缺口可能来自提取质量、人工动作、导出形式或使用流程。

## D-008：长期北极星与近期定位分层

- **状态**：已确认（2026-08-27）
- **决定**：长期北极星为“本地认知工作台”；近期正式定位为“面向研究型创作者和深度阅读者的、本地优先的‘阅读到观点’工作台”。
- **边界**：不把读见表述为通用认知平台、NotebookLM 替代品或万能研究工具。
- **原因**：现有能力已覆盖阅读、结构提取和本地沉淀，但尚未覆盖多来源研究、协作、通用知识管理或云端工作流。

## D-009：用户确认后的认知产物优先于自动摘要

- **状态**：已确认（2026-08-27）
- **决定**：战略上的最终价值对象是“用户确认后的认知产物”，而非 AI 摘要，也不立即把“观点”设为唯一系统数据中心。
- **说明**：观点卡、证据、异议、Creator Brief 和修订后的框架都是候选表现形式；是否持久化为新数据结构必须先由真实使用证明。
- **原因**：保留用户判断位置，避免以未来架构替代产品验证。

## D-010：Owner 验证贯穿路线，Challenge 保持轻量

- **状态**：已确认（2026-08-27）
- **决定**：路线采用“可靠提取 + Owner 真实内容闭环 → 最小人工校准 → 轻量观点卡 / Creator Brief → 轻量 Challenge → 候选外部 ICP 验证”。
- **说明**：Owner 使用不是后期单独阶段；Challenge 第一阶段可由固定 Prompt 或检查清单实现。
- **不做**：多 Agent、状态机、推演树、评分体系和大型 simulation engine。

## D-011：人工校准是用户资产，Creator Brief 先验证后产品化

- **状态**：已确认（2026-08-27）
- **决定**：人工校准首先服务用户对材料的理解与修订，不默认成为开发者数据资产。Creator Brief 第一阶段只作为 Markdown 模板与工作流验证。
- **隐私边界**：未来若考虑用户自愿贡献匿名校准数据，必须单独获得明确 opt-in，并完成隐私、授权与法律设计。
- **不做**：当前不创建专用 Creator Brief 数据库、复杂 UI 或独立生成中心。

## D-012：商业化依赖真实使用证据

- **状态**：已确认（2026-08-27）
- **决定**：商业顺序为“Owner 自用与内容产出 → 小规模外部验证 → 信任资产并行积累 → 根据真实证据决定软件收费”。
- **说明**：按书收费不是默认第一模式；Free / Pro、买断、年费、社群与课程均是待验证选择。
- **原因**：当前 API 成本由用户 BYOD 承担，且项目尚无真实商业验证。

## D-013：能力状态必须显式标注

- **状态**：已确认（2026-08-27）
- **决定**：正式文档必须区分 `Current`、`Prototype / Experimental`、`Candidate / Planned`、`Deferred`、`Historical / Superseded`。
- **原因**：当前工作区、`v1.1.0` 标签与 `origin/main` 并非同一事实层；文档不得把计划、工作区改动或发布版本混写。
