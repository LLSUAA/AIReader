## 一、先说结论（三句话）

1. **"AI 总结文档"是红海，单靠这个功能我们打不过 NotebookLM，这是事实，不需要争论。**
2. **但我们的产品定义不是"总结器"，是"深度阅读方法论"**——把"怎么读一本书"封装成可交互的流程（四技能 → 全书框架 → 溯源 → 沙盘推演）。这个品类目前没有大厂占据。
3. **真正的护城河候选排序：沙盘推演 > 校准数据 > 工作流闭环 > 垂直人群**。CFI 溯源不是护城河本身，而是让其他一切都"可验证"的地基。

## 二、竞品对比（诚实版）

| 维度 | NotebookLM | Readwise Reader | Glasp | AIReader（现状） |
|------|-----------|-----------------|-------|------------------|
| 核心定位 | 多文档资料问答 | 阅读 + 高亮管理 | 网页高亮 + 分享 | 本地深度阅读 + 结构化提取 |
| 上传/来源 | 云端多文档 | 云端订阅 + 自行导入 | 网页端 | BYOD 本地（EPUB/TXT） |
| AI 形态 | 被动问答 + 音频简报 | 被动问答 + 摘要 | 被动总结 | **主动陪读按钮（方法论封装）** |
| 溯源 | 引用标注（较好） | 一般 | 无 | 实验性 CFI（暂缓，见 §五） |
| 结构化产出 | 一般（笔记/问答） | 高亮导出 | 网页片段 | **全书骨架 + Mermaid + 导出 Markdown** |
| 推演/训练 | 无 | 无 | 无 | **沙盘推演（规划中，见 §六）** |
| 数据隐私 | 云端 | 云端 | 云端 | **本地优先，无服务器** |
| 中文深度阅读 | 一般 | 一般 | 一般 | **原生中文场景** |

**结论**：在"读得舒服"和"资料问答"上我们不可能赢，也不需要赢。我们的战场是**"读完之后留下什么"**——产出物的结构化程度、可验证程度、可交互程度。

## 三、差异化三支柱（我的核心判断）

### 支柱 1：主动陪读方法论（已有，是灵魂）

Readwise 的 AI 是一个"聪明的搜索框"——用户得会提问。我们的四个按钮把"该怎么读一本书"的方法论封装成了动作：复盘/骨架/解释/推演。用户不需要会提问，点一下就行。

这是 qwen 第一次讨论时也认可的点（"把读书方法封装成按钮，这是产品哲学的差异"）。**模型会变，方法论不会变**——这是所有支柱里最抗通胀的资产。

### 支柱 2：结构化提取管线 + 可验证性（已有 80%，CFI 暂缓）

一本书 → 全书骨架 + 每章要点 + 概念关系图 + 论证主线，每一条都能对应到原文位置。对比：

- NotebookLM 的引用是"资料来源"级别的（这段来自哪个文档）；
- 我们要做的是"**论点级溯源**"（这条论点来自这本书的第几章第几段）。

这是信任度的生死线。用户敢不敢把 AI 提取的框架用于复习/决策，取决于能不能随时回原文验证。

**诚实说明**：CFI 溯源当前实现不稳定（单章大书/嵌套文档下翻页定位失效），已封存。但这只是工程问题，方向没有错——见 §五。

### 支柱 3：沙盘推演（规划中，最独特）

把一本书变成"**可推演的思维模型**"：用户读《资本论》，不是问"这本书讲了什么"，而是被系统丢进一个极端情境，被迫用书里的逻辑做推演、被批阅、再复盘。

NotebookLM 和 Readwise **都没有这个形态**。大厂不做，因为这是"训练"而不是"检索"，需要方法论文档支撑、需要用户投入时间——但恰恰是深度阅读者愿意投入的。

## 四、护城河分析（诚实版 + 可建设版）

### 4.1 现状：没有真正的护城河

- 提取管线：技术门槛中等，别人 2-4 周能抄；
- Prompt 设计：会被模型升级抹平；
- 本地优先：是差异化，但不是护城河（技术上谁都能做）；
- 执行领先：我们领先的只是"已经跑通 + 踩过坑"，时间窗口有限。

**所以 qwen 上次的判断依然成立：最大风险不是技术，是没人知道产品存在 + 护城河还没建起来。**

### 4.2 可以积累的四层护城河（按优先级）

**第一层：校准数据（最容易被忽视，最持久）**
每本书提取后做人工校准（改标题、删错误条目、标注来源章节），把校准结果回写为"这本书的结构化知识库"。模型会换代，但"如何拆解一本好书"的校准数据不会。100 本校准书 = 别人抄不走的语料资产。

**第二层：框架说明书体系（沙盘推演的前提）**
用户的宏观笔记（04 传导骨架 / 05 宏观经济学详解 / 08 中国制度 / 09 结构）已经是一套框架系统。把它们固化成"推演约束说明书"（变量、传导路径、观察指标、禁入结论），就是沙盘推演的"笼子"——没有笼子的推演是高级幻觉，有笼子的推演是训练工具。

**第三层：工作流闭环（粘性）**
阅读 → 提取 → 校准 → 推演 → 沉淀到 Obsidian 知识库 → 回读时溯源。用户一旦把知识库建在这个工作流上，迁移成本极高。

**第四层：垂直人群（获客）**
中文宏观/投资深度阅读者。人群小但付费意愿和传播力强（读书笔记天然可分享）。

### 4.3 时间窗口判断

大厂（Google/Notion/Readwise）短期内不会做"本地优先 + 垂直方法论 + 推演训练"组合：
- 本地优先与他们的云端商业模式冲突；
- 推演训练需要用户投入，不适合大众产品；
- 中文宏观书拆解太小众，不值得大厂进场。

这个窗口期是我们的机会，但也意味着**获客只能靠内容**（拆书笔记就是内容），不能靠渠道。

## 五、CFI 溯源：为什么封存但方向不变

### 5.1 定位

溯源是"可验证性"的地基，没有它，提取结果和 NotebookLM 的摘要没有本质区别（都是"AI 说了算"）。

### 5.2 封存原因（技术复盘）

- 构建期生成 CFI：spine item 的 cfiBase 取值不稳定，生成的 CFI 缺章节组件 → 全部落到首页；
- 运行时文本定位 + `contents.cfiFromRange()`：在多章 EPUB 上可跳章节；在**单章大书 / 嵌套容器（blockquote 内嵌 p）文档**上，命中段落错乱（startText 重复）或坐标翻页不生效（`locationOf` 返回零坐标）；
- epub.js 0.3 对"已显示章节"走坐标滚动而非重渲染，嵌套文档下坐标解析不稳定。

### 5.3 未来修复方向（不承诺时间）

1. 放弃依赖 epub.js 的 locationOf，点击时**强制重渲染目标章节**后再 display(cfi)；
2. 为单章大书建立"段落索引 → 页码"缓存（提取时预计算，点击时查表）；
3. 必要时引入 `book.locations.generate()`（以性能为代价换精确页码）。

**替代方案（轻量，可先做）**：溯源链接点击后只保证"跳到正确章节 + 高亮该段落的文字位置"（滚动到段落而非精确页码），降低对 epub.js 内部行为的依赖。

## 六、沙盘推演：完整设想

### 6.1 定位

先是**个人工具**（服务自己的宏观学习），再验证是否可作为付费功能。这是 qwen 与我的一致判断：成败标准是"你自己用不用、信不信"，不是"有没有人买"。

### 6.2 一句话定义

> 把一本书（或一套笔记）的框架固化为"推演约束说明书"，AI 只在这个约束内出题、批阅、复盘，绝不给确定性结论。

### 6.3 设计要素

1. **框架说明书**：从全书骨架 + 用户宏观笔记生成，包含：核心变量、传导路径、关键观察指标、历史锚点、禁止项（不给点位/涨跌/选举结果等确定性预测）。
2. **三档推演模式**：
   - 概念推演（检验理解）：把概念逼到边界条件；
   - 情境推演（检验应用）：给定现实情境，要求用框架推演传导链；
   - 剧本推演（检验综合）：多变量组合的极端剧本，要求输出"路径 + 观察指标 + 分叉点"。
3. **盲盒锁死（已有雏形）**：先独立作答（≥30 字），AI 批阅后才解锁；批阅要指出"哪一步跳出了框架、哪一步有事实错误"。
4. **复盘循环**：推演记录沉淀为知识晶体（已有收藏机制），标注"框架内/框架外"，积累成自己的认知轨迹。
5. **信任护栏**：系统提示明确"推演不是预测，禁止用于真实投资决策"；所有推演结论必须可回溯源文档（这里 CFI 溯源的价值才真正兑现）。

### 6.4 与竞品的差异

- NotebookLM：资料问答 → 我们：用资料做压力测试；
- Readwise：读完即走 → 我们：读完还要过一遍"试炼"；
- 通用 AI 聊天：随意提问 → 我们：在框架约束内推演 + 强制独立作答。

### 6.5 技术落点

- 复用提取管线：framework_markdown + 章节要点就是推演的"教材"；
- 新增 `skills/simulation.js`：框架说明书生成器 + 推演会话状态机（出题→作答→批阅→复盘）；
- 沿用现有 API 层（requestJSON/streamAIResponse）与知识晶体存储；
- 不引入 RAG/向量库（与 qwen 一致：现阶段不需要）。

### 6.6 风险

- **幻觉风险**：框架约束只能降低不能消除；靠"禁止确定性结论 + 强制溯源 + 复盘"三道护栏；
- **用户投入成本高**：推演比阅读累，适合的只是深度学习者——所以先服务自己，验证"累但值得"；
- **变现场景不明**：可能永远只是个人工具，接受这个可能。

## 七、需要与 qwen 讨论的开放问题

1. **优先级**：沙盘推演 vs 人工校准入口 vs CFI 修复，先做哪个？（我的建议：人工校准入口先做，因为它同时喂饱"校准数据"护城河和"沙盘教材"质量；CFI 修复缓行。）
2. **付费形态**：如果沙盘推演做成付费功能，按次/订阅/捆绑"拆书服务"哪种更合适？（我的倾向：不单独卖沙盘，卖"深度拆书服务"时作为增值，先验证拆书本身有没有人买。）
3. **本地优先是否坚持**：本地优先限制了协作/分享/多端，但保护了隐私差异化和零服务器成本。什么时候值得放弃？（我的倾向：在出现真实付费用户之前不放弃。）
4. **校准数据是否有价值**：个人开发者积累的"100 本校准书"数据，是否真的能形成壁垒，还是只是自我感动？（我的判断：有壁垒，但前提是校准质量高且沉淀成结构化格式，不是随手改两笔。）
5. **内容获客的可行性**：用拆书笔记在小红书/V2EX/即刻获客，在无内容团队的情况下是否现实？（我的判断：现实，因为产出物本身即内容，但需要先积累 10-20 本高质量样本。）
